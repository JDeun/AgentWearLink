## Python versus C++ policy

[Python framing, L38–42 and L159–236](https://github.com/facebookincubator/muse-gadget-sdk/blob/1b894f551e64416e2844452ec6056ec56d6a10f1/linux/src/musegadget/noise/framing.py#L159-L236) supports up to 16 pending assemblies, up to 256 chunks each, with expiry on the next decode after 60 seconds measured from creation using wall clock. [C++ framing, L90–99](https://github.com/facebookincubator/muse-gadget-sdk/blob/1b894f551e64416e2844452ec6056ec56d6a10f1/esp32/components/noise_core/include/xplat/noise/core/TransportFrameCodec.h#L90-L99) derives a 257-chunk ceiling from the 16 MiB logical limit and 65,489-byte chunk payload. [Ordered assembly, L614–695](https://github.com/facebookincubator/muse-gadget-sdk/blob/1b894f551e64416e2844452ec6056ec56d6a10f1/esp32/components/noise_core/src/TransportFrameCodec.cpp#L614-L695) has one active message and requires matching ID/count/next index; no clock in this core. Python permits out-of-order chunks and rejects duplicates while an assembly is active; C++ rejects order mismatch/duplicate during active assembly and poisons. These are source-level policy differences, not an assertion of interoperability failure on the ordered common subset. Per-assembly maximum is not aggregate process heap. Owner must impose hard byte/time/slot bounds; AWL reliable control must never use lossy media-style resync.
